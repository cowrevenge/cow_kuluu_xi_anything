# 0x100dc1f0 - what actually happened, and the fix that must be applied ATOMICALLY

## Root cause of the 394 re-verify failures (verified 2026-11-11)

The unit's source referenced `clock->cleared_before_tick`. `layout/structs.h` renamed that field to
`tick_wrap_count` (+0x4c, and its own doc comment still says "f_100dc1f0 clears it just before taking a
tick"). The rename was never carried across, so the file stopped compiling.

An object file from when it DID compile was sitting in `build/`, masking the error. The independent
re-verify forced a fresh build (mtime touch), the error surfaced, and the unit was DELETED from the tree
instead of being fixed. One minute later a `recomp.py` pass regenerated `generated/all/{funcs.h,table.c,
funcs_014.c}` **from a tree that no longer contained the unit**, so `table.c` lost its
`rt_wrap_cow_100dc1f0` definition.

Verified with a control: `table.c` holds 3 hits for each neighbouring address (decl, table entry, wrap
definition) and only 1 for `100dc1f0` - the table entry survives, the wrap definition is gone.

Consequence: guest address 0x100dc1f0 is no longer routed to our adapter, so on OUR side it now runs the
generated `f_100dc1f0`. Every unit whose execution reaches it changed behaviour. **Measured: this
accounts for ~204 of the 394 (the deep-state class), not all of them - see
`cow/wip/reverify-classes-20261111.md`.** **Do not un-prove the remainder either; report them.**

## The fix - three steps, one commit, tree otherwise quiet

1. `cp cow/wip/100dc1f0/cow_100dc1f0_stamp_net_clock_tick.c src/net/` - this copy already has the
   `cleared_before_tick` -> `tick_wrap_count` rename and compiles clean (`cl /Zs`, rc 0).
2. Restore the three `100dc1f0` lines in `runtime/cow/cow_wraps.c` (extern / adapter decl / install).
   `git diff 43587c62^ -- runtime/cow/cow_wraps.c` is the exact inverse; a restoration was confirmed
   byte-identical before being reverted.
3. Regenerate `generated/all/table.c` so it DEFINES `rt_wrap_cow_100dc1f0` again.

Step 3 cannot be skipped: with only 1+2 the link fails `LNK2019: unresolved external
rt_wrap_cow_100dc1f0 ... referenced in cow_install_wraps`.

## WARNING before step 3

`table.c` is generated by scanning the SOURCE TREE, and `generated/` is **gitignored** - so a regeneration
is an un-versioned change to the judge itself. The main tree currently carries **2,796 untracked,
uncommitted `src/lifted/*.c`** files belonging to another session's in-flight re-lift. Regenerating here
would silently fold that unproven work into the ground truth and any verdict after it would be
unattributable - the exact trap that produced this 394-unit mess.

Do step 3 in a clean worktree containing only HEAD plus the restored unit, or after the re-lift is
committed.

ours=10313417` cluster (136 units), which fails at **state 0** with or without the wrap - so it is

ledger; do not treat it as the cure for 136 genuine defects, which remain open.
