# 0x102e7f5a - reading in progress (handed out by loopy, 215 bytes, 90 sites, 1 callee)

Disassembled in full (tools/cow/disasm.py 0x102e7f5a 0x102e8031). What the entry does, from the
listing alone - nothing here is verified yet and there is no src/ file, no seed and no mutation.

## Frame and signature
- `push ebp / mov ebp,esp / sub esp,0x74 / push esi / push edi`, epilogue
  `pop edi / pop esi / leave / ret 0x20` -> stdcall, eight arguments.
- Arguments actually referenced: [ebp+0x8] (the object whose vtable is called), [ebp+0xc],
  [ebp+0x10], [ebp+0x14] (esi), [ebp+0x18] (edx), [ebp+0x1c] (the angle), [ebp+0x20] (ecx),
  [ebp+0x24]. That is 8 words from +0x8 to +0x24 -> the `ret 0x20` matches eight.
- esi/edx/ecx are each tested for NULL and, when non-NULL, their two dwords are copied into a
  pair of frame slots; when NULL the pair is left UNINITIALISED except that one float of the pair
  is stored as 1.0f (esi case, [ebp-0x1c] via fld1) or 0.0f (edx and ecx cases, fldz). So the
  three groups are "a caller-supplied pair, or a default": (ebp-0x24,-0x20 / -0x1c), 
  (-0x18,-0x14 / -0x10), (-0xc,-0x8 / -0x4).
- [ebp-0x34,-0x30] and [ebp-0x2c,-0x28]: the sin/cos group, only written on the branch taken when
  the angle compares to [0x103295d8] in a particular way.

## The float tests (both use the same constant, but NOT the same instruction)
- 0x102e7f93 `fcom dword ptr [0x103295d8]` then `fnstsw ax / test ah,0x44 / jnp` - **equal only**,
  not "equal or unordered": 0x44 masks ah bits 2 and 6 = C2 and C3, fcom leaves C3C2 = 00 for
  greater, 00 for less, 10 for equal, 11 for unordered, and `jnp` takes on odd popcount - so only
  the 10 (equal) case jumps. The jump lands past the trig block, so the block runs when the angle
  is NOT +0.0f/-0.0f (NaN counts as unordered and DOES run it). Inside it the entry stores two
  zeros and computes `fld [0x1032a3d0]; fmul st(1); fld st(0); fsin -> [ebp-0x2c]; fcos ->
  [ebp-0x28]`. `fmul st(1)` is st(0)*st(1) - confirmed against side A's
  `x87_s0 = fr_cw(x87_cw, x87_s0 * x87_s1)` - and [0x1032a3d0] is -1.0f, so this is sin(-angle)
  and cos(-angle) of ONE value (the `fld st(0)`), with the angle itself left on the stack.
- 0x102e7fd5 `fcomp dword ptr [0x103295d8]` - the SAME constant, this one POPS, and its `jnp`
  jumps to `xor eax,eax` (fall-through is `lea eax,[ebp-0x34]`). So eax is the trig-buffer pointer
  when the angle is non-zero and NULL when it is zero: the two tests are ONE decision read twice,
  and the buffer is only ever handed out on the path that filled it. Inverting either of them
  alone would pass a pointer at four uninitialised words.

## The select that is not a select
- 0x102e7fe2 `lea eax,[ebp-0x34]` / `jmp` vs 0x102e7fe7 `xor eax,eax`: eax is either a POINTER to
  the sin/cos group or 0, and it is pushed as an argument. So the callee at 0x102d7e83 takes a
  possibly-NULL pointer to the trig group.
- 0x102e7fe9-0x102e8007: three `neg r / sbb r,r / lea / and r,frame_addr / push r` sequences - the
  classic "if (p) &p else 0" idiom WITHOUT a branch, on esi, edx, ecx. So each of the three
  pointer args becomes "address of its frame pair, or 0" - the NULL the caller passed is forwarded
  as 0, and the pair's uninitialised half is therefore never read by the callee. That is why the
  uninitialised slots are not a bug and why a conversion must reproduce the zero, not the bytes.

## The two calls
- 0x102e8010 `call 0x102d7e83` with six pushes: the three-or-zero pair pointers, the trig pointer
  or 0, 0, 0, and `lea eax,[ebp-0x74]` - the 0x48-byte stack buffer, which is the OUT parameter
  (18 floats? 0x48 = 72 bytes = 18 dwords - likely a 4x4 matrix plus two floats, must be checked
  against what 0x102d7e83 writes).
- 0x102e8015-0x102e8028: `push [ebp+0x24]`; eax = [ebp+8]; ecx = [eax] (the VTABLE); push the
  buffer; push [ebp+0x10]; push [ebp+0xc]; push eax; `call dword ptr [ecx+0x18]` - slot 6 of the
  object's vtable, five arguments.

## Resolved since the first pass (do not re-investigate)
- **Both "constants" are zero and minus one.** `0x103295d8` = 00 00 00 00 = +0.0f and `0x1032a3d0` =
  00 00 00 bf = -1.0f (tools/cow/peek_bytes.py --len 4). So the guard is the angle against ZERO
  (`fcom`/`fcomp` +0.0f, `test ah,0x44`/`jnp` = C0|C2 set = equal-or-unordered, i.e. 0.0f or NaN),
  and the trig argument is `-1.0f * angle`, computed once and used by both `fsin` and `fcos`
  through `fld st(0)`. They are image reads, not literals, so they go in layout/addresses.h and the
  adapter reads them with rdf32 - the same way f_102da2b2 reads its -2.0f and 1.0f.
- **fsin/fcos: use the CRT directly.** The generated side A is literally
  `x87_s0 = fr_cw(x87_cw, sin(x87_s0)); g->c2 = 0;` (generated/all/funcs_050.c at 0x102e7fb4), and
  the harness pins fcw=0x027F so PC=double makes fr_cw the identity. There is no fsin/fcos helper in
  runtime/guest.h - nothing to ask. Precedent for writing `sin()`/`cos()` in a user function:
  src/geom/cow_102d8be9_quaternion_from_axis_angle.c (cow_quaternion_from_axis_angle) does exactly
  that and passes. Store the sine as a float first and multiply with the ROUNDED float, as that unit
  does, because 0x102e7fb6 stores it and the later uses read the word back.
- **0x102d7e83 is a table thunk, not a routine**: `jmp dword ptr [0x103cc4ac]` (five bytes, then an
  unrelated function at 0x102d7e89). Bridge it, never convert - same treatment as
  COW_ADDR_VECTOR4_TABLE_THUNK, and the seed must STUB it, because the slot's file image is the
  unconverted refresh trampoline and the fuzzed states will recurse through it and take the
  harness's stack down (that is exactly what bit f_102da2b2/f_102da1d8). Note this thunk takes SIX
  dwords of arguments and the entry cleans them with its own `ret 0x20`, so the bridge pushes none
  (see the note at the top of the net-clock block in layout/calls.c about site-exact bridges).
- **The vtable call needs NEW machinery.** `call dword ptr [ecx+0x18]` where ecx = the vtable read
  from [ [ebp+8] ]. Side A emits
  `esp -= 4; wr32(esp, retaddr); rt_call_indirect(g, t);`. NO unit under src/ or layout/ has ever
  called rt_call_indirect - it is declared in runtime/guest.h:103 and used by the harness itself
  (runtime/portable/gthread.c:241). So this unit needs the first bridge for it in layout/calls.c,
  e.g. a `cow_call_vtable_slot(Guest*, uint32_t target)`-style helper, and the seed must pin the
  object AND its vtable row so the slot resolves to something that returns. Expect the vtable object
  to be the hard part of the seed: [ebp+8] must point at an arena word whose value is a pointer to
  a pinned row of function addresses, and a fuzzed one faults on both sides (agreement, not proof).
